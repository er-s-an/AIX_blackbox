# 06 · 字段映射表（x402 / AP2 / Mastercard VI → AFR）

> 目的：PRD v1.3 §10.1 要求的"字段命名参考"证据。**这是命名与语义对照，不是兼容性声明；AFR 不实现任何一方的协议。**
> 外部字段名依据公开材料（x402 GitHub README/spec；AP2 公开规范摘要；Mastercard VI 2026-03 公告与公开结构描述）。外部规范会变化，提交前复核。

## 1. x402（`PaymentRequirements` / `PaymentPayload`）→ AFR

| x402 字段 | 含义 | AFR 对应 | 差异说明 |
|---|---|---|---|
| `scheme` (`exact`) | 支付方案 | – | AFR P0 为直接 ERC-20 转账；x402 exact 在 EVM 用 EIP-3009 `transferWithAuthorization` 经 facilitator 结算 |
| `network` | 链标识（CAIP-2 风格） | `anchors_expected[].chain_id` = 1439 | Injective 不在 x402 已支持网络列表 |
| `maxAmountRequired` | 最大金额（最小单位整数字符串） | `mandate.message.per_tx_cap`（18 位小数十进制字符串） | 单位表示不同：整数 wei vs 十进制字符串 |
| `asset` | 代币合约地址 | `mandate.message.currency` (`AFR-TEST-USD`) + trust `contracts.test_token.address` | AFR 以符号为主，地址在信任配置 |
| `payTo` | 收款地址 | `evidence` 中支付请求事件的 `payee`；约束来自 `scenario.supplier_registry.suppliers[].payee` | AFR 收款人约束是登记集合，不是单地址 |
| `resource` | 被购买资源 URL | `scenario.supplier_registry.suppliers[].endpoint` + 支付请求事件 `resource` | 一致 |
| `description` | 资源描述 | `mandate.message.task`（意图）/ supplier `declared_capabilities`（供给） | AFR 分成意图与供给两侧 |
| `maxTimeoutSeconds` | 结算超时 | Gateway 内部 `Failed` 超时 | 语义近似 |
| `extra` | 方案扩展 | – | – |
| `PaymentPayload.payload.authorization` (EIP-3009) | 转账授权签名 | – | AFR 无此对象；Agent 钱包由 Gateway 持钥直接发交易 |
| （无） | – | `mandate.*` 全部 | x402 没有"用户事前授权 Agent 花钱"的对象；这是 AFR/AP2/VI 层 |

结论：字段命名可对照，结算模型不同。PRD 措辞"字段命名参考 x402"成立；"兼容 x402"不成立。

## 2. AP2（Agent Payments Protocol）Mandate/Receipt → AFR

| AP2 概念 | 含义 | AFR 对应 | 差异 |
|---|---|---|---|
| Intent Mandate | 用户表达的购物意图与约束（可含 human-not-present 授权） | `AFRMandate.task / total_budget / per_tx_cap / valid_*` | AFR 无购物车/商户协商流程 |
| Cart Mandate | 具体购物车（商品、价格）由用户签署 | 无直接对应；F03 夹具中的"用户二次确认"证据在语义上最接近 | AFR 的 `confirmation_mode=human_second_confirm` 产出的确认事件 ≈ Cart Mandate 的签署时刻 |
| Payment Mandate | 传给支付网络的授权与代理标志 | 支付请求证据事件 | AFR 不接支付网络 |
| Receipt | 商户/网络回执 | `evidence` 支付回执事件 + 链上回执 | 一致 |
| Verifiable Credential 包装 | VC/JWT 签名容器 | EIP-712 + EIP-191 | 容器不同 |

结论：AFR Mandate ≈ AP2 Intent Mandate 的子集；命名前缀 `AFR` 以避免混淆。

## 3. Mastercard Verifiable Intent → AFR

| VI 结构（公开描述） | 含义 | AFR 对应 | 差异 |
|---|---|---|---|
| Layer 1：身份凭证（用户 / agent 身份） | 谁在交易 | `mandate.signer`、`mandate.message.agent_wallet`、`trusted_signers` 角色 | AFR 无 KYC 身份层 |
| Layer 2：用户签署的约束（预算、商户、期限） | 用户授权了什么 | `AFRMandate` 全部约束字段 | 高度对应 |
| Layer 2：agent 履约凭证（agent 声明依约行动） | agent 的行动声明 | Gateway 签名的支付请求事件 + `verifier_statement` | AFR 由 Gateway/验证者签，非 agent 自签 |
| Action / Transaction record 绑定 | 意图与结果绑定的防篡改记录 | `manifest` 承诺 + 链上锚定 | VI 用 SD-JWT 链，AFR 用哈希承诺 + 链上存证 |
| Dispute 场景可查 | 争议时各方可查 | 证据包 + CLI | **VI 覆盖到此为止**；AFR 增加：外部输入语义偏离、结算后交付有效性、净损失、条款映射、人工处置、恢复执行 |

结论：VI 已覆盖"授权—行动—结果绑定"；AFR 的差异化必须在表格最后一行右侧。§10 已按此改写。
